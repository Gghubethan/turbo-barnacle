# ⑤ JD 匹配

有目标 JD 时做。没有 JD 就跳过，并在诊断报告里说明"未针对具体岗位优化"。

## 第一步：拆 JD

把 JD 拆成三类，逐条落表：

| 类型 | 识别信号 | 权重 |
| --- | --- | --- |
| **硬性要求** | "必须""要求""至少 X 年""本科及以上" | 不满足基本被筛 |
| **加分项** | "优先""加分""有…者优先" | 差异化来源 |
| **隐含要求** | 从岗位职责反推的能力、团队规模、业务阶段（0→1 还是规模化） | 决定你该突出哪段经历 |

隐含要求最值钱：JD 写"负责从 0 到 1 搭建数据体系"，说明他们要的是**搭建者**不是**维护者**——你简历里的搭建类经历就该提到最前面。

## 第二步：关键词提取

抽出 JD 的**能力词 / 工具词 / 业务词**，与简历比对。三种状态：

- ✅ **已覆盖且措辞一致** —— 不动。
- 🔄 **已覆盖但措辞不同** —— 这是唯一可以"改词"的情况。把简历里的同义表达换成 JD 的说法（"用户分层" → JD 用"用户分群"就跟着用）。ATS 关键词匹配靠字面。
- ❌ **未覆盖** —— **不许加**。只有三条路：
  1. 用户其实做过但没写 → 问用户，确认后按事实补（这是补，不是编）。
  2. 有相邻经验可以诚实类比 → 写真实的那个，不假装是 JD 要的那个。
  3. 确实没有 → 列进 gap，让用户自己判断要不要投。

**绝不 keyword stuffing**：塞一堆没做过的词，ATS 过了、面试挂得更难看，且这属于编造，违反铁律。

## 第三步：匹配打分

```
硬性要求覆盖率  4/5   （缺：3 年经验，你 2 年 —— 可投，需在其他项拉高）
加分项覆盖率    2/4
隐含要求匹配    强 / 中 / 弱

综合结论：建议投 / 建议投但需调整重点 / 优先级放低
```

打分要给**证据强度**，不只是有没有：

| JD 要求 | 简历证据 | 强度 | 说明 |
| --- | --- | --- | --- |
| SQL 数据分析 | 工作经历第 1 段第 2 条：搭建看板 | 强 | 有具体产出 |
| 用户增长 | 技能栏写了"熟悉增长模型" | 弱 | 只有词，没有事 |

**"只有词没有事"是最常见的假匹配**，要明确指出来——这类要么补事实，要么删掉别占位置。

## 第四步：产出建议

JD 匹配的结论**不是"重写简历"**，通常只有三种动作：

1. **调顺序**：把 JD 最看重的经历/条目往前提（零成本，收益最大）。
2. **换措辞**：同义词对齐 JD 用语（零风险）。
3. **调篇幅**：压缩无关经历，给相关经历腾出空间。

如果一份简历要为某个 JD "大改特改"，那说明岗位不匹配——**直接把这个判断告诉用户**，比帮他硬凑更有价值。

## 多岗位投递

用户投多个方向时，不要做一份"什么都沾"的简历——那是最差解。建议主版本 + 按方向的轻量变体（只改顺序和摘要，正文共用），并在 `resume-work/` 下分文件保存。
