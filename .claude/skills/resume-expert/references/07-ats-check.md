# ⑦ ATS 兼容检查

ATS（Applicant Tracking System）会先把简历**转成纯文本**再做关键词匹配。所有"人眼好看但机器读不出来"的设计，都是在给自己减分。国内大厂/外企/海外投递普遍有这一层。

## 自动扫描

```bash
python3 .claude/skills/resume-expert/scripts/ats_check.py resume-work/原简历.docx
python3 .claude/skills/resume-expert/scripts/ats_check.py resume-work/简历.pdf --json
```

脚本查的是**机器可判定项**，输出带 🔴/🟡/⚪ 分级：

| 检查项 | 判定 |
| --- | --- |
| 文本能否提取 | 提不出 = 🔴 致命（扫描件/图片版） |
| 分栏（`w:cols`>1 / PDF 双栏坐标分布） | 🔴 双栏会让机器把左右两栏的文字交错串行 |
| 文本框 `w:txbxContent` | 🔴 多数解析器直接丢弃文本框内容 |
| 表格承载正文 | 🟡 简单表格多数能读，嵌套/合并单元格 🔴 |
| 图片 / 图表 / 图标 | 🟡 图里的信息等于没写；纯装饰无妨 |
| 页眉页脚含联系方式 | 🔴 常见解析器不读页眉页脚，等于没留电话 |
| 字体是否常见 | 🟡 冷门字体在对方机器上会回退，排版全乱 |
| 特殊符号项目符号（❖ ✦ ▪ 等） | 🟡 转文本可能变成乱码或问号 |
| 页数 | 参考 `06-layout-review.md`（借 LibreOffice 转 PDF 数页，没有则按字数估算） |
| 联系方式格式 | 电话/邮箱能否被正则抓到；邮箱里有空格、电话被拆成两段 = 🔴 |
| 日期格式一致性 | 🟡 混用会让时间线解析出错 |

脚本查不了的，人工判断（下面两节）。

## 人工判断项

1. **模块标题用标准名**：用「工作经历 / 教育背景 / 项目经历 / 技能」，别用「我的江湖」「战绩」这类创意标题——ATS 按标题分段，认不出就归不了类。英文用 Work Experience / Education / Projects / Skills。
2. **关键词与 JD 字面一致**（见 `05-jd-match.md`），但**不许堆砌没做过的词**。
3. **缩写 + 全称至少出现一次**：`A/B 测试（AB test）`、`SEO（搜索引擎优化）`——机器和人各认一半。
4. **文件格式**：没有明确要求时投 **DOCX**（解析最稳）；要求 PDF 时确保是**文字版 PDF**（能选中文字），不要"打印成图片"。
5. **文件名**：`姓名-目标岗位-简历.pdf`，不要 `简历最终版最终版2.pdf`。
6. **不要把关键信息只放在这些地方**：页眉、页脚、文本框、图片、批注、水印。

## 关于"ATS 分数"

网上很多"ATS 通过率 XX%"是营销话术，各家系统实现差异很大。这套流程**不给虚构分数**，只给：

```
致命问题 0 项 ｜ 高风险 2 项 ｜ 建议优化 3 项
结论：当前版本可以安全投递 / 有 2 项必须修复后再投
```

## 与排版阶段的关系

ATS 发现的问题绝大多数在阶段 ⑧ 排版时一并解决：`build_docx.py` 生成的就是单栏、无文本框、无表格布局、标准字体、标准 bullet 的结构。所以顺序是**先 ATS 扫原件（拿到问题清单）→ 排版修复 → 对产物再扫一次确认清零**。
